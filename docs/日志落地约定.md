# 医学报告质控系统日志落地约定

依据：[通用项目日志规范](通用项目日志规范.md)。用户于2026-10-15指定本规范为项目日志要求；原文完整保留，其 recognition/csrcqsf 路径为来源示例，不代表本项目已有实现。本文只将通用规范映射到本项目的目录、进程和业务字段；当前仍为实施要求，日志代码尚未编写。

## 1. 统一配置与输出

- 日志库使用 **Loguru**，唯一配置入口为 `backend/app/core/logging_config.py`；业务模块从该入口导入logger，不自行add sink，不用print代替服务日志。API、worker、GPU、retrieval、recovery和运维脚本共用这一个轻量模块，导入它不得连带加载数据库或模型。
- 接口：`configure_logging(log_root:Path,*,service:str,instance_id:str,reset:bool=False)->None`。入口在初始化业务组件前调用；首次启动移除Loguru内置默认sink避免重复stderr输出；同进程默认幂等，reset只移除本模块管理的输出目标并重建，不能误删其他库的handler。
- 控制台写 **stdout、INFO及以上**，TTY显示颜色，重定向后无颜色。文件写 **DEBUG及以上、UTF-8、无颜色**。格式为 `时间 | 等级 | 文件名:函数名:行号 - 消息`，文件/函数/行号定位到实际业务调用处。bind字段必须通过消息/formatter真实输出，无请求日志提供默认上下文，不能只bind后假定文本里已有request_id。
- 中文描述动作及实际结果，后接固定英文字段 `业务动作及结果: key=value, key=value`；Loguru使用 `{}` 占位符，标准logging转发前保持其自身格式化语义，禁止混用 `%s`。
- `APP_LOG_DIR` 是绝对日志基目录，默认 `<项目根>/var/logs`；本项目继续使用既定var目录，不依赖cwd。实际传入配置器的log_root为该基目录，文件隔离路径为 `<APP_LOG_DIR>/<service>/<instance_id>/pid-<pid>/app/app_YYYY-MM-DD.log`，保留规范中的app子目录及文件名。service固定为api/worker/gpu/retrieval/recovery或具体运维命令，instance_id由部署配置显式提供且限制安全字符。
- 文件按 **Asia/Shanghai每日00:00** 切分、保留 **30天**、ZIP压缩；部署为各服务设置TZ=Asia/Shanghai。业务数据库和API时间仍UTC，日志当地时间规则不能改变数据时间契约。
- 文件目录不可写：WARNING说明脱敏路径和原因，stdout继续可用，不误报文件日志初始化成功。重复配置不重复输出。多进程/实例不共用同一轮转文件。
- Uvicorn、Celery及需纳管的标准库logging经统一桥接到Loguru，仅一套handler；access log不与请求中间件重复。明确第三方日志输出归属，限制SQL/HTTP调试日志，防止打印正文、请求头或SQL参数。
- 首版使用同步sink，避免增加未验收的日志队列；后续若开启enqueue，必须验证跨进程隔离及退出前 `logger.complete()` 刷完，不允许退出丢日志。Loguru设置 `diagnose=False`，traceback不捕获局部变量。

## 2. 字段与追踪

| 日志字段 | 本项目含义 |
| --- | --- |
| request_id | 当前HTTP调用或后台执行继承的追踪编号；从受校验的X-Request-ID读取或生成，JSON响应与响应头返回同值 |
| task_id | quality_run.id，跨分支、重试及进度查询保持一致；未建立run的导入/导出任务使用其自身持久ID |
| item_id | run_report.id；原始文件行号另记original_row |
| module_result_id / generation | 持久工作单元ID及本次执行代际 |
| inference_request_id | GPU/检索DTO内用于幂等的request_id；与HTTP追踪request_id分开记录 |
| celery_task_id | 可选传输层消息ID，不替代稳定业务task_id |
| stage | 采用总计划已定义的diagnosis.generate/csc.correct/cgec.teacher等阶段名 |
| status | 当前所记录对象的真实业务状态；不把queued当成已经执行完成 |
| response_status | API外层success/error；与task执行状态分开 |
| attempt / max_attempts | 日志统一使用这两个字段；分别映射持久attempt_no和阶段总尝试上限3，不改数据库字段名 |
| error_code / error_type / error_message | 映射ErrorDetail.code/exception_type/message，统一命名并脱敏 |
| duration_ms | perf_counter测量的实际耗时，单位毫秒 |
| service / http_status | 调用目标和真实HTTP状态；自有错误http_status=200时仍记response_status=error与error_code |
| total / processed_count / success_count / fail_count / skipped_count | 明确scope的同一工作单元集合计数，不能混用报告异常数与执行成功数 |

异步请求用contextvars/Loguru contextualize隔离；Celery线程、GPU队列线程和恢复命令须显式设置并在finally中恢复上下文，不能依赖跨线程自动继承或全局“当前request_id”。持久保存origin_request_id并将其传入StageContext（新增可选request_id字段）；发往内部服务的X-Request-ID沿用该追踪编号，模型请求payload中的request_id继续用于幂等，两种编号不能互换。

新建/重试/查询HTTP请求可以有不同request_id，task_id保持稳定；日志记录对应操作的origin_request_id。没有HTTP来源的定时任务自行生成追踪ID。请求ID校验长度/字符，不能将含换行或控制字符的外部值原样写日志。

## 3. 各场景的等级和记录时机

- 初始化：逐步记录数据库、队列、模型、索引的开始/完成/失败与耗时；必需依赖失败记CRITICAL并按启动策略终止/保持not_ready，不记录虚假“全部启动完成”。
- HTTP：中间件记录method、path（不含query）、http_status、response_status、request_id及duration_ms；应用错误即使200也保留error_code。正常空结果/校验/无权限按影响记INFO或WARNING，不一律ERROR。
- 后台：INFO记录持久提交、实际开始、阶段变化、每批或约30秒的节流进度及最终结果；逐条成功细节放DEBUG。outbox落盘只代表pending/已提交，broker确认发布才记录已入队，不能将其写成执行完成。
- 重试：可恢复失败用WARNING，真实发生的attempt/max_attempts和耗时准确；最终失败用ERROR。查询同一在途GPU请求不是新attempt，不得在日志中虚增重试次数。
- 统计：成功、失败、跳过按同一scope互斥。工作单元完成数 `processed_count=success_count+fail_count+skipped_count`；skipped_count只包含被取消且未完成的单元，pending/running不计完成。取消/部分失败时另记pending_count/running_count/cancelled_count，不能把未处理单元算成功。报告issue/needs_review/incomplete统计可能重叠，单列其真实业务字段，不参加上述互斥和式。
- 异常：通常由最终负责结束/处理操作的边界，在except内使用 `logger.exception()` 或 `logger.opt(exception=...).error()` 记录一次完整堆栈；下层补上下文并 `raise ... from exc`，不重复打印整条traceback。重试中的WARNING默认只记录异常摘要；最终工作单元/HTTP边界记录完整链。GPU等跨进程边界各记录本进程最终异常，依靠request_id/inference_request_id关联。
- 数据库保存失败后重新抛出供Celery/恢复接手，logging桥接须避免Celery再次重复输出同一异常堆栈；不能为了去重吞掉异常。finally仅做清理/计时，不无条件记录成功。

## 4. 脱敏、长度与保留

禁止密码、Authorization、Cookie、token、连接凭据、签名URL、完整配置/SQL参数、报告正文、完整prompt/response、向量和20候选正文进入普通日志。记录ID/hash/长度/候选数量/索引版本；必要原始响应继续在受控attempt/artifact审计存储，不替代持久业务事实。

外部error_message最多 **1000个字符**，移除换行和控制字符后按allowlist脱敏。异常消息与格式化堆栈同样检查敏感值；保留真正堆栈的帧换行，但净化不可信异常内容，不能把控制字符注入日志伪造业务行。`diagnose=False`不能替代脱敏。响应detail展示仍按此前HTTP200/error约定执行。

普通日志文件保留30天；raw审计默认30天可配置，业务结果/证据不自动删除。按pid隔离留下的旧进程目录也必须由运维清理程序纳入30天回收，不能只依赖活跃sink的retention；先校验目标在APP_LOG_DIR内，只删除超过保留期的关闭文件/ZIP及空目录，跳过当前活动日志。部署验证切分、压缩、权限、磁盘占用和退出写完；保留天数不是磁盘容量上限。

## 5. 实施与验收对应

| 归属任务 | 必须验证 |
| --- | --- |
| A1 | configure_logging幂等/reset、console/file等级、UTF-8/颜色、调用点、不可写fallback、30天/午夜/ZIP配置、脱敏、标准logging桥接与context隔离 |
| A3/A4/A7 | request/task/item/attempt贯穿与持久映射，日志状态真实；HTTP200/error准确记录；异常只在负责边界记录完整堆栈，重试不刷屏 |
| B2/B3/B5 | 模型/检索初始化过程、内部追踪头与幂等ID分离；外部错误1000字上限/净化；GPU线程不串上下文 |
| D5 | 各unit时区/APP_LOG_DIR/instance_id，进程隔离、30天清理（含旧PID目录）及磁盘检查，日志查询命令 |
| D6 | 单条/批量/失败/取消/重启用task_id追全程；并发日志无串号；脱敏和业务计数正确；部署验证每日切分与ZIP |

测试使用临时目录、受控sink/时钟和合成数据，不为验证轮转修改主机时钟，也不在业务目录故意写满磁盘。所有日志实现完成后才可以在验收记录中写“日志规范已落地”。

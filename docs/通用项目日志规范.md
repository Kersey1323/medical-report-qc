# 通用项目日志规范

本文依据 recognition 项目的日志实现整理，适用于 Python API 服务、定时任务和后台任务。迁移到其他项目时，将示例中的 `your_project` 替换为实际包名即可。

## 1. 当前项目的实现依据

| 内容 | 当前实现 |
| --- | --- |
| 主服务日志库 | Loguru |
| 统一配置入口 | `csrcqsf/core/logging_config.py` |
| 控制台 | 标准输出 stdout，INFO 及以上，带颜色 |
| 日志文件 | DEBUG 及以上，不带颜色 |
| 文件格式 | `时间 \| 等级 \| 文件名:函数名:行号 - 消息` |
| 文件位置 | `<APP_LOG_DIR>/app/app_YYYY-MM-DD.log` |
| 默认目录 | 应用根目录下的 `logs/app/` |
| 切分与归档 | 运行环境当地时间每日 00:00 切分，保留 30 天，ZIP 压缩 |
| 重复初始化 | 默认不重复添加输出目标；显式重置时重新配置 |
| 文件目录不可写 | 输出告警，保留控制台日志 |
| 启动阶段 | 记录每个初始化步骤的开始、完成、失败和耗时 |

当前项目仍有部分模块使用标准库 `logging`，主服务日志也尚未统一附带请求编号。下文的字段约定、脱敏和请求追踪等属于迁移时建议采用的规范，不代表本项目已经全部实现。

## 2. 基本原则

一条日志应当让维护人员知道：**发生了什么、影响哪个对象、结果如何、为什么失败。** 涉及网络调用或耗时任务时，还要说明耗时。

- 在统一模块配置日志；业务模块只导入并使用，不自行添加文件或控制台输出。
- 用中文说明业务行为，用固定的英文字段名记录编号、数量和耗时。
- 日志描述实际结果。任务提交成功只代表进入队列，不能写成任务执行完成。
- 不用 `print()` 代替服务日志；独立命令行工具的结果输出不受此限制。
- 一次异常通常由负责处理或结束该操作的层记录完整堆栈，下层补充异常信息后向上抛出，避免重复刷屏。
- 日志用于排查问题，任务状态、用户反馈和审计记录等重要业务数据仍应持久化，不能只写日志。

## 3. 日志等级

| 等级 | 使用场景 | 示例 |
| --- | --- | --- |
| DEBUG | 排查需要的细节，正常运行不必在控制台逐条展示 | 某批数据的筛选数量、单张图片处理结果 |
| INFO | 业务正常推进的重要节点 | 服务启动、任务提交、任务完成、批次进度 |
| WARNING | 出现异常或降级，但仍能继续处理 | 外部服务短暂失败、使用本地缓存、重试即将开始 |
| ERROR | 当前请求、任务或子项最终失败 | 重试耗尽、数据写入失败、任务执行失败 |
| CRITICAL | 服务整体无法正常运行 | 必需配置缺失导致启动终止 |

不是所有非成功响应都应记录 ERROR。参数错误、无权限、查询无结果等预期情况，按业务影响记录 INFO 或 WARNING；不要把正常的空结果当作系统异常。

## 4. 消息格式与字段

统一使用：

```text
业务动作及结果: key=value, key=value
```

例如：

```text
2026-10-15 14:30:01 | INFO | sync_service.py:run:120 - 图片同步完成: task_id=task-001, total=100, success_count=96, fail_count=4, duration_ms=18450
```

按业务需要记录以下字段，不要求每条日志全部填写：

| 字段 | 含义 |
| --- | --- |
| `request_id` | 一次 HTTP 请求的编号，用来关联该请求中的多条日志 |
| `task_id` | 后台任务编号，跨重试和状态查询保持一致 |
| `item_id` / `history_id` | 操作的业务对象编号；其他项目可换为订单编号等 |
| `stage` | 失败或执行所在阶段，例如 download、upload、persist |
| `status` | 当前结果，例如 queued、running、succeeded、partial、failed |
| `duration_ms` | 耗时，统一使用毫秒 |
| `total` / `processed_count` | 总量、已处理数量 |
| `success_count` / `fail_count` / `skipped_count` | 成功、失败、跳过数量 |
| `attempt` / `max_attempts` | 当前第几次尝试、总共允许几次，均包含首次请求 |
| `error_code` | 稳定的业务错误码，便于统计和定位 |
| `error_type` / `error_message` | 异常类型、经过脱敏的异常说明 |
| `service` / `http_status` | 外部服务名称、HTTP 状态码 |

同一含义不要交替使用 `err`、`error`、`reason` 等不同字段。日志中的 `status` 应与实际业务状态一致。

## 5. 常见场景记录要求

### 5.1 接口请求

记录请求编号、方法、路径、HTTP 状态码和总耗时。使用路径部分，不直接记录可能含 token 的完整 URL。

```text
请求处理完成: request_id=req-001, method=POST, path=/items/search, http_status=200, duration_ms=328
```

建议由统一中间件生成或校验 `request_id`，在响应中返回，并传给后台任务和下游服务。异步请求的上下文应使用 `contextvars` 或 Loguru 的 `contextualize()` 隔离，不能使用全局变量保存当前请求编号。

### 5.2 后台任务与批量处理

记录提交、实际开始、阶段变化、定期进度、最终结果。长任务建议每处理一个批次或每隔 30 秒记录一次进度，避免 INFO 级别逐条打印所有成功记录。

```text
图片同步已提交: task_id=task-001, status=queued
图片同步开始: task_id=task-001, total=1000, status=running
图片同步进度: task_id=task-001, processed_count=200, success_count=190, fail_count=3, skipped_count=7
图片同步结束: task_id=task-001, status=partial, processed_count=1000, success_count=950, fail_count=20, skipped_count=30, duration_ms=320000
```

成功、失败和跳过的定义应互斥。任务完成时应能核对数量；取消或中途失败时，不要把尚未处理的数据算为成功。

### 5.3 外部接口与重试

失败日志要包含外部服务、HTTP 状态码、错误消息、耗时及是否继续尝试。响应为 500 时，尽可能提取响应中的业务 `message`，但必须限制长度并脱敏，不能只记录“调用失败”。

```text
外部图片下载失败，将重试: service=image_source, task_id=task-001, item_id=123, http_status=503, attempt=1, max_attempts=3, duration_ms=2000, error_message=服务暂不可用
外部图片下载最终失败: service=image_source, task_id=task-001, item_id=123, http_status=500, attempt=1, max_attempts=1, error_message=源文件不存在
```

记录实际执行的重试策略，不在日志里声称已重试尚未发生的请求。重试中的可恢复失败通常记录 WARNING，最终失败记录 ERROR。

### 5.4 启动与降级

数据库、存储、队列等初始化分别记录开始、完成和耗时。可选功能未配置时说明哪些能力被跳过；必需依赖失败时记录堆栈并按启动策略终止，不输出“启动完成”。

## 6. Python 写法

### 6.1 Loguru 使用花括号占位符

```python
from your_project.core.logging_config import logger

logger.info("任务已提交: task_id={}, item_id={}", task_id, item_id)
logger.warning("图片下载失败，将跳过: item_id={}, http_status={}", item_id, status)

try:
    await save_result()
except Exception:
    logger.exception("结果保存失败: task_id={}, stage=persist", task_id)
    raise
```

`logger.exception()` 在异常处理块内使用，自动附带当前异常堆栈。需要记录堆栈时，不要只写 `logger.error(str(exc))`，也不要重复拼接 `traceback.format_exc()`。

Loguru 与标准库 logging 的占位符不能混用：

```python
# Loguru
logger.info("任务已提交: task_id={}", task_id)

# 标准库 logging
standard_logger.info("任务已提交: task_id=%s", task_id)
```

### 6.2 正确记录异步操作耗时

使用 `time.perf_counter()`，不使用系统时钟计算耗时。异步操作必须等待执行结束后再记录结果。

```python
from time import perf_counter

started = perf_counter()
try:
    result = await process_item(item_id)
except Exception:
    logger.exception(
        "配件处理失败: item_id={}, duration_ms={:.1f}",
        item_id,
        (perf_counter() - started) * 1000,
    )
    raise
else:
    logger.info(
        "配件处理完成: item_id={}, duration_ms={:.1f}",
        item_id,
        (perf_counter() - started) * 1000,
    )
```

不能在 `finally` 中无条件打印“处理成功”；异常路径也会执行 `finally`。

## 7. 敏感信息与日志体积

- 不记录密码、Authorization、Cookie、完整 token、数据库连接密码或带签名的下载地址。
- 不打印整个环境配置、请求体、外部响应或 SQL 参数；按允许的字段提取必要信息。
- 不把图片、视频、Base64、完整向量和大批候选结果写入日志。记录对象编号、文件大小、候选数量等摘要。
- 外部错误消息建议最多保留 1000 个字符，并移除换行和控制字符，避免伪造额外日志行。
- 需要关联敏感输入时，优先使用编号或摘要；异常消息和堆栈也可能包含敏感内容，需要检查。
- 生产环境建议关闭 Loguru 的变量诊断：`diagnose=False`，避免堆栈展示局部变量值。

## 8. 可复用的最小配置

下面是迁移模板，保留本项目的主要输出习惯，并补充 UTF-8 和关闭变量诊断。它不是当前项目配置文件的原样复制。

```python
# your_project/core/logging_config.py
import sys
from pathlib import Path

from loguru import logger

CONSOLE_FORMAT = (
    "<green>{time:YYYY-MM-DD HH:mm:ss}</green> | "
    "<level>{level}</level> | "
    "<cyan>{file.name}:{function}:{line}</cyan> - <level>{message}</level>"
)
FILE_FORMAT = (
    "{time:YYYY-MM-DD HH:mm:ss} | {level} | "
    "{file.name}:{function}:{line} - {message}"
)
_configured = False


def configure_logging(log_root: Path) -> None:
    global _configured
    if _configured:
        return

    logger.remove()
    logger.add(
        sys.stdout,
        level="INFO",
        format=CONSOLE_FORMAT,
        colorize=sys.stdout.isatty(),
        diagnose=False,
    )
    app_log_dir = log_root / "app"
    try:
        app_log_dir.mkdir(parents=True, exist_ok=True)
        logger.add(
            app_log_dir / "app_{time:YYYY-MM-DD}.log",
            level="DEBUG",
            format=FILE_FORMAT,
            rotation="00:00",
            retention="30 days",
            compression="zip",
            encoding="utf-8",
            diagnose=False,
        )
    except OSError as exc:
        logger.warning("文件日志初始化失败: path={}, error={}", app_log_dir, exc)

    _configured = True
```

在应用入口、启动业务组件之前调用一次 `configure_logging()`。日志根目录由应用配置解析并传入，使用绝对路径，不依赖启动命令所在目录。

## 9. 部署与兼容要求

- 统一部署时区。需要北京时间每日零点切分时，应确认运行环境时区为 `Asia/Shanghai`；当前项目的日志配置本身没有强制设置时区。
- 容器环境保留 stdout 输出，文件日志按需要挂载持久化目录。保留 30 天不是容量上限，还应监控磁盘占用。
- 多个 worker 或多个容器不要各自独立轮转同一个文件；优先统一收集 stdout，或按实例、进程分开文件。
- 存在标准库 logging、Uvicorn 或第三方日志时，明确它们由谁输出。需要统一格式时单独配置转发，避免重复记录；仅调用 `logger.remove()` 不会清理标准库 logging 的处理器。
- `logger.bind(request_id=...)` 只附加字段，默认文本格式不会自动显示这些字段。需要请求编号时，应把字段写入消息或配置对应格式，并为无请求上下文的日志提供默认值。
- 需要机器检索时可以新增 JSON 输出；字段必须实际写入记录，不能只在文档中约定。
- 高频日志、排队写入和压缩策略应结合实际负载评估；启用异步队列写日志后，退出前需要等待日志写完。

## 10. 迁移验收

1. 控制台能看到 INFO、WARNING、ERROR，并能定位文件、函数和行号。
2. DEBUG 写入文件，不出现在默认控制台。
3. 重复初始化不会使一条日志输出多次。
4. 日志目录不可写时有明确告警，控制台仍可使用。
5. 一次任务能通过 `task_id` 找到提交、执行和最终结果。
6. 异常有堆栈，正常无结果不会产生误导性的系统错误。
7. 日志不含密码、token、文件正文或完整环境配置。
8. 日期切分、保留、压缩及多进程写入方案经过部署验证。
